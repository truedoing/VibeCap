# 模型部署与优化

> VibeCut 的所有 AI 模型都跑在 CPU 上——一台 MacBook。从 BGE 嵌入到 Whisper 语音识别，关键在"不用 GPU 也能干活"的优化策略。

## 是什么

模型部署与优化 = 在有限的硬件资源上，让 AI 模型跑得快、占用少、不联网也能工作。

VibeCut 的部署环境：MacBook（macOS），无 NVIDIA GPU，16GB RAM。需要同时跑 3 个模型：BGE 语义编码（768 维）、faster-whisper 语音识别、DeepSeek API 远程调用。

## 为什么需要这些优化

| 没有优化 | 有优化 |
|---------|--------|
| BGE 加载 5 秒，内存 2GB | mmap 加载 0.1 秒，内存 ~500MB |
| Whisper large-v3 需要 10GB 显存 | int8 量化后 CPU 可用 |
| 每次启动从 HuggingFace 下载模型 | HF_HUB_OFFLINE=1 离线加载 |
| 国内下载 HuggingFace 超时 | hf-mirror.com 国内镜像 |

## 关键概念

### 1. CPU 推理 vs GPU 推理

```
GPU 推理:                     CPU 推理:
┌──────────────────┐          ┌──────────────────┐
│ CUDA/cuDNN 加速   │          │ 无硬件加速        │
│ 批量编码 1000条/秒 │          │ 批量编码 50条/秒  │
│ 需要 NVIDIA GPU    │          │ 任何电脑都行      │
│ 模型加载到显存    │          │ 模型加载到内存    │
└──────────────────┘          └──────────────────┘
```

VibeCut 选择 CPU 推理的原因很简单：开发机没有 GPU。对于单用户场景，CPU 编码速度完全够用——搜索一次编码 1 个 query，只需几十毫秒。批量建索引时编码上万条较慢，但跑一次就行。

### 2. mmap 零拷贝加载

```python
# 传统加载：把整个文件读入内存（~500MB npy → 500MB RAM）
embeddings = np.load("semantic_embeddings.npy")

# mmap 加载：文件映射到虚拟内存，按需读取（~500MB npy → ~50MB RAM 常驻）
embeddings = np.load("semantic_embeddings.npy", mmap_mode='r')
```

`mmap_mode='r'` 告诉 numpy 不要把整个文件读入内存。操作系统在需要访问某一行向量时才从磁盘加载对应的页面。这对 10 万条向量的索引尤其重要——100MB+ 的文件不能全部常驻内存。

VibeCut 在 `server.py` 中的加载优先级：

```python
if INDEX_NPY.exists():
    semantic_emb = np.load(INDEX_NPY, mmap_mode='r')  # 优先 mmap
elif INDEX_FILE.exists():
    old = pickle.load(open(INDEX_FILE, "rb"))  # pickle 兜底
```

### 3. int8 量化（faster-whisper）

```python
# faster-whisper 默认使用 int8 量化
from faster_whisper import WhisperModel
model = WhisperModel("large-v3", device="cpu", compute_type="int8")
```

量化 = 把模型参数从 float32（4 字节）压缩到 int8（1 字节），模型大小缩到 1/4。代价是精度轻微下降，但 ASR 任务对精度不敏感——差 0.01% 的字错率完全可接受。

### 4. HF 离线模式与国内镜像

```python
# server.py 启动时设置
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")   # 国内镜像
os.environ.setdefault("HF_HUB_OFFLINE", "1")                     # 离线模式
os.environ.setdefault("TRANSFORMERS_OFFLINE", "1")               # 离线模式

# build_index.py 加载模型时
model = SentenceTransformer("BAAI/bge-base-zh-v1.5",
                           local_files_only=True)  # 强制不联网
```

三条环境变量的作用：

| 环境变量 | 作用 |
|----------|------|
| `HF_ENDPOINT` | 指定 HuggingFace 的镜像地址（国内访问 hf.co 很慢） |
| `HF_HUB_OFFLINE` | huggingface_hub 库不发起任何网络请求 |
| `TRANSFORMERS_OFFLINE` | transformers 库不检查模型更新 |

首次使用时需要联网下载模型（走 hf-mirror.com），之后 `local_files_only=True` 确保离线可运行。

### 5. 模型预热

```python
# server.py 启动时异步预热 BGE 模型
threading.Thread(target=lambda: _agent_search("预热", limit=1), daemon=True).start()
```

为什么需要预热？BGE 模型第一次编码时会加载词表、初始化计算图。如果不预热，用户的第一个搜索请求会卡 5-8 秒。启动时异步预热，等用户发出第一个请求时模型已经就绪。

## 在 VibeCut 中的应用

**`server.py`**（第 17-59 行）：
- 设置离线模式环境变量
- 注入搜索函数到 Agent 系统
- 异步预热 BGE 模型（最多等 30 秒）

**`build_index.py`**：
- `local_files_only=True` 强制离线加载
- 批量编码时使用 `show_progress_bar=True` 追踪进度
- npy float32 保存（比 float64 省一半空间）

## 动手实验

1. **观察模型缓存位置**
```bash
ls ~/.cache/huggingface/hub/ | grep bge
# 确认 BGE 模型已在本地缓存，可以离线使用
```

2. **对比 mmap vs 普通加载的内存占用**
```python
import numpy as np, os, psutil
# 普通加载
emb1 = np.load("semantic_embeddings.npy")
print(f"普通加载: {psutil.Process().memory_info().rss / 1024**2:.0f} MB")
del emb1

# mmap 加载
emb2 = np.load("semantic_embeddings.npy", mmap_mode='r')
print(f"mmap加载: {psutil.Process().memory_info().rss / 1024**2:.0f} MB")
```
