# RAG 评估方法

> 怎么证明"我的检索/生成质量还行"——指标、工具、和 VibeCut 的实践

## 为什么评估难

RAG 有两个环节，各有各的评估问题：

```
检索 (Retrieval)         生成 (Generation)
──────────────          ────────────────
有客观答案 → 可量化      主观性强 → 难量化
"搜到的对不对"           "生成的像不像样"
recall@k / MRR / NDCG    LLM-as-Judge / 人工
```

**VibeCut 的特殊性：** 检索结果不只是"给 LLM 看的"，还要**落到时间轴上成为视频画面**——所以评估必须包含"检索到的画面是否符合导演意图"这种主观判断。

## 一、检索质量评估（可量化）

### 1. 核心指标

| 指标 | 含义 | 怎么算 |
|------|------|--------|
| **Recall@k** | 前 k 个结果里含多少个正确答案 | 命中数 / 总正确答案数 |
| **Precision@k** | 前 k 个结果里正确的占比 | 命中数 / k |
| **MRR** | 第一个正确答案排得多靠前 | 1 / 首个命中的排名 |
| **NDCG** | 正确结果按相关性排序的加权分 | 位置越靠前分越高 |

```python
# 例子：查询"苏明成打明玉"，正确答案在场景3
# 检索返回 [场景1, 场景3, 场景5]
# recall@3 = 1/1, MRR = 1/2 (第一个命中的排名是2)
```

### 2. 评估数据集（Ground Truth）

需要一组"查询 → 期望命中的块"的标注：

```
{"query": "苏明成为什么打明玉", "expected": ["ep21/scene2", "ep21/scene3"]}
```

**VibeCut 里的做法：** 用分镜脚本的解说词作查询，期望命中的是它对应的场景——因为解说词就是"基于这些画面写的"，天然有对应关系。

## 二、端到端生成评估（难量化）

### 1. LLM-as-Judge（LLM 当裁判）

用另一个 LLM 按标准打分：

```python
prompt = """你是评审。判断以下回答是否忠实于参考资料：
参考资料: {context}
回答: {answer}
按 1-5 分打分，标准：事实准确性、完整性、引用正确性。"""
```

**优点：** 便宜、快、可重复。**缺点：** 评判 LLM 也有偏见（喜欢长答案、喜欢自己的风格）。

### 2. 人工评估（Human Eval）

最可靠但有成本。**分级抽样**：全部自动跑，只抽一部分人工复核。

### 3. 幻觉检测

- **上下文忠实度**：回答里的每个事实点是否都能在 context 里找到
- **引用验证**：回答标注的 [来源: EP5 120s] 是否真在上下文里

## 三、VibeCut 的评估实践

### 1. 数据质量评分（自动）

`GET /data/quality` 给每集打分：字幕 + VLM + scene_map + 概要的完整度加权。

```json
{
  "ep": 21, "vlm": 33, "asr": 756,
  "vlm_score": 96, "scene_map_score": 100
}
```

### 2. Agent Harness（行为评估）

[[Agent测试与评估]] 里的五部件 Harness：对概率性 Agent 行为（导演选择哪个镜头）做结构校验 + 语义判断，而不是断言精确输出。

### 3. 人工核对闭环（VibeCut 特色）

因为检索结果要变成画面，VibeCut 引入了**人工复盘**机制：
- 分镜大纲里每个镜头显示对应 VLM 详情 → 一眼核对"画面是否匹配解说词"
- 时间轴删除不合适 clip → 大纲标记 🗑已删 → 复盘哪些镜头被淘汰
- 人物权威用 scene_map（字幕+LLM），不信 VLM 人脸 → 把 29% 的认人错误从源头掐断

**核心思路：** 机器指标（recall/MRR）保证"没有系统性失灵"，人工复盘兜住"主观是否合适"。

## 四、评估迭代闭环

```
1. 建立 ground truth（查询→期望结果）
2. 跑指标（recall@k / MRR）
3. 定位失败（哪些查询没命中，为什么）
4. 改进（换切分策略 / 调嵌入 / 改检索权重）
5. 重测 → 看指标是否上升
```

**VibeCut 案例：** 最初按固定窗口切 ASR，检索"苏明成打明玉"命中零散台词；改成按 scene_map 场景切后，场景级召回明显提升——**一次切分策略的改动，靠指标对比证明价值**。

## 常见坑

1. **只看 recall 不看 precision**：搜出一堆不相关的结果也拉高 recall
2. **ground truth 太少**：几十条查询的指标没统计意义
3. **评估集污染**：用来评估的查询在训练/开发时见过，指标虚高
4. **只看生成不看检索**：生成差可能是检索差导致的，先查检索
