# Agent 应用测试框架设计

> 状态：设计草案 v1 · 2026-08-13
> 背景：RAG 闭环测试（V1→V5）暴露出 Agent 应用测试的本质问题——LLM 输出的不确定性，让传统断言式测试失效，需要引入「对比评估」。

## 一、核心判断：Agent 测试 = 传统测试 + 对比评估

传统软件测试断言的是「确定性正确」，Agent 应用的 LLM 输出是「概率性质量」。两者不是替代关系，是**分层**：

| | 传统软件测试 | Agent/LLM 测试 |
|---|---|---|
| 正确性 | 确定性（输入→输出唯一） | 概率性（输入→分布） |
| 断言方式 | `assert 输出 == 期望` | 「质量分数 ≥ 阈值」 |
| 失败信号 | 崩溃 / 报错 / 返回值错 | 「质量不达标」（但没崩） |
| 适用对象 | 纯函数、API、UI 流程 | 生成内容、检索质量、Agent 决策 |

**结论**：Agent 应用里，代码天然分两类，测试也分两层——

```
        ▲
       / \         E2E + 评估：跑完整 pipeline，对比评估质量
      /   \
     / 评估 \      ← 新增层：LLM 输出的对比评估（传统测试没有这一层）
    /-------\
   / 集成测试 \    ← 断言 pipeline 编排正确（步骤顺序、数据传导）
  /-----------\
 /  单元测试   \   ← 断言纯函数/确定性逻辑
/---------------\
```

## 二、Harness：Agent 测试的核心工具

### 定义

**Harness = 把被测对象「套住」、反复喂输入、收集输出、按固定标准评分的那一层脚手架。**

- 原意「马具」：套在马身上驾驭它的那套东西。
- 软件里：套在被测代码外面的、驱动它和评判它的框架。

### Harness vs Agent

| | Agent | Harness |
|---|---|---|
| 智能 | 有，能自主决策 | 无，确定性代码 |
| 干什么 | 生成解说词、反推剧集 | 喂输入、抓输出、打分 |
| 可预测 | 不可（概率输出） | 可（普通代码） |
| 角色 | 被测对象（考生） | 测试工具（考场+试卷+评分标准） |

### Harness 的五个部件

| 部件 | 作用 |
|---|---|
| ① 被测对象适配 | 封装被测函数的调用 |
| ② 固定输入（金标准案例） | 可复跑的 case + ground truth |
| ③ 输出采集 | 抓结构化输出字段 |
| ④ 评分器 | 把「模糊质量」变成「可比较分数」 |
| ⑤ 模式开关 | 跑不同策略 / 版本做对比 |

## 三、关键设计原则：Harness 对应「被测边界」，不是「一个 Agent」

一个 harness 套哪一层，取决于「你想测什么」。不是"一个 harness 锁死一个 Agent"。

### 被测边界 × 评估点 × 成本（本项目的拆解）

| Harness | 套哪个边界 | 评什么 | LLM 调用 | 成本 |
|---|---|---|---|---|
| **A · 检索** | `_infer_episodes_from_topic_llm` | 反推的集准不准 | 1 次 | ~9s |
| **B · 故事师** | `story_master_agent` | story_map 质量 | 1 次 | ~30s |
| **C · 端到端** | `run_drama_pipeline` | 完整脚本质量 | 4+ 次 | ~80s |

**教训（来自 RAG 闭环测试）**：现有 `test_rag.py` 套的是 C（最大边界），评的却是 A（检索准不准）——**边界和评估点错位**，导致每次白跑后面三步（策划师+文案师+校验）。

### 正确姿势：先定「测哪层」，再选 harness 粒度

- 只想测"反推剧集准不准" → 用 harness A，别用 C。
- 只想测"整条流水线端到端" → 才用 harness C。

## 四、确定性部分 vs 概率性部分（现有代码切分）

`drama_script_agents.py` 里两类代码混在一起，应分别对待：

### 确定性（该用 pytest 单测，`assert`）

| 函数 | 断言点 |
|---|---|
| `_load_scene_maps` | 返回 `{ep: [scene,...]}` 结构、ep 过滤正确 |
| `_load_all_synopses` | episodes 参数过滤生效（浅层 RAG 的关键） |
| `_emotion_signature` | 冲突/缓和/转折计数正确（纯函数） |
| `_infer_episodes_from_topic` | for 循环反推逻辑（确定性） |
| Phase 4 校验 | time_range 对齐、episode_marker 填充 |

### 概率性（该用 harness 评估，`质量分数`）

| 边界 | 评估指标 |
|---|---|
| 深层 RAG 反推 | 命中「真实弧线节点」数（非人工指定集） |
| 故事师 | story_map 完整性（人物弧光/转折点是否覆盖选题） |
| 文案师 | scene_query 与 scene_map 一致性（张冠李戴率） |

## 五、评估指标升级：从「命中人工指定」到「覆盖真实弧线」

RAG 闭环测试暴露：**人工指定集本身有偏差**（EP35 苏明成线是"与舅舅对立"，EP41 是"关系紧张的低谷"，而非"守护终点"；真实终点是 EP37/45）。

因此评估指标不能用"命中人工指定的 5 集"当 ground truth，而应改用**「覆盖真实弧线节点」**：

- ground truth 从「人工凭记忆标注」→ 「scene_map / 结构化 synopsis 里可验证的弧线节点」
- 评分 = 反推结果覆盖多少个「真实弧线关键节点」（起点/转折/高潮/终点）

## 六、落地路线（分三步，从便宜到贵）

| 步骤 | 内容 | 成本 | 状态 |
|---|---|---|---|
| 1 | 确定性部分补 pytest 单测 | 0 LLM、毫秒级 | ✅ 完成（13 个，0.27s） |
| 2 | 把 `test_rag.py` 升级成 harness A（只测检索层，拆掉陪跑） | 1 次 LLM/案例 | ✅ 完成（3 案例，平均召回 0.60） |
| 3 | 建金标准案例集 + 端到端 harness C（CI 用） | 4 次 LLM/案例 | ✅ 完成（3 案例，全维度） |

**原则**：先做最便宜、最确定性的（pytest 单测），再做检索层 harness，最后才做端到端。

### 已落地实现

- **单测**：`tests/test_drama_deterministic.py` — 13 个确定性测试，`pytest tests/ -v`
- **检索 harness**：`tests/harness_retrieval.py` — 3 个金标准案例，只调 `_infer_episodes_from_topic_llm`（~9s/案例）
- **文案师事实准确性 harness**：`tests/harness_writer_factuality.py` — 度量 scene_query vs scene_map 的张冠李戴率
- **E2E harness**：`tests/harness_e2e.py` — 全维度（硬门槛 + 事实 + 语言质量 LLM 评分）

### 文案师事实准确性 harness 实测（2026-08-13）

**多次采样版（`--runs 5`）揭示：单次错误率波动极大，必须采样取平均。**

优化前后对比（5 次采样）：

| 指标 | 优化前 | 优化后（加"原样复制"铁律） |
|---|---|---|
| 平均错误率 | 6.69% | **3.75%**（↓44%） |
| 事件错误 | 3 | **0** |
| 人物错误 | 1 | **0** |
| 情绪错误 | 5 | 5（未降） |

**结论**：
1. "scene_query 字段原样复制"规则对**事件/人物**维度是特效药（错误归零）。
2. **情绪维度降不下来，根因在 ground truth 本身**：scene_map 有 13 个词表外 mood 标签（"感慨""震惊""神秘"等，占 0.86%），且部分场景 mood 标注与语义相悖（如"苏明成觉醒"标成"激烈"）。LLM 在"忠实复制错误标签"和"按语义写正确情绪"之间矛盾。

**洞察**：harness 的价值不止于"测出文案师漂移"，更在于**反向暴露了 scene_map（数据资产）的 mood 标签噪声**——这印证了「事实校验引擎」的正确性边界：校验的上限，取决于 ground truth 的质量。

**下一步方向**（三选一）：
- A. 修 scene_map 的 mood 标签（治本，但需重跑场记Agent或人工校订 13 个词表外标签）
- B. 事实校验对 mood 降权/放宽容忍度（情绪语义相近即算一致，不要求逐字相等）
- C. mood 校验改用"语义相近"而非"字面相等"（用 LLM 或情绪词表映射判断"感动≈感慨"）

### 治本落地（方案 A）—— mood 标签规范化

诊断发现：scene_map 只有 **13 个词表外 mood**（0.86%），且语义全对（坚定/震惊/感慨…），只是场记Agent 偶尔用了词表外精确词。**并非"情绪标注烂了"**。

- 新增 `cli/normalize_mood.py`，把 13 个词表外标签映射回标准 15 词（坚定→严肃、感慨→感动、震惊→紧张…），带 `--dry-run` + 写回校验
- 词表单一事实来源对齐：`lib/scene_map.py` / `handlers/prompts/script_drama.py` / harness 三处 15 词统一

**三阶段错误率（5 次采样）**：

| 阶段 | 平均错误率 | 情绪 | 事件/人物 |
|---|---|---|---|
| ① 基线 | 6.69% | 5 | 4 |
| ② +原样复制铁律 | 3.75% | 5 | 0 |
| ③ +mood 规范化（治本） | **1.57%** | 2 | 0 |

总降幅 76.5%。剩余 1.57% 是 LLM 主观情绪判断的固有噪声（"尴尬 vs 感动"），已触及词表规范化的上限，属可接受范围。

### 检索 harness 实测（2026-08-13）

| 案例 | ground truth（真实弧线节点） | 召回率 |
|---|---|---|
| 苏明成人物线 | 21,32,37,39,45 | 0.8 |
| 苏明玉人物线 | 21,38,39,42 | 0.5 |
| 苏大强人物线 | 44,45 | 0.5 |

平均召回 0.60。ground truth 从结构化 synopsis 的 `character_arcs` 提取，而非人工标注——这正是"评估指标升级"的落地。

### E2E harness 实测（2026-08-13）

全维度评估揭示：**事实准确性（0%）、语言质量（4.4-4.8/5）、硬门槛（全过）都达标**。时长是**参考指标，不是生产门槛**——解说脚本的真实时长由配音台 TTS 决定，`total_chars/4` 只是粗估。

两个阻断问题在本次一并修复：

| 问题 | 根因 | 修复 |
|---|---|---|
| DB 丢字段 | `save_task_segments` 读扁平键 `episode_marker_ep`，但真实字段是嵌套 `episode_marker`；`video_episode` 无 DB 列 | 提取嵌套字段 + 新增 `video_episode` 列 |
| export_capcut 定位失败 | drama 的 `source="AI编剧Agent"` 占位符，glob `*.mp4` 找不到 | 新增 `find_source_video_for_episode` 按集号定位 |

> 注：export_capcut 属「剪映导出」环节，严格说不在"编剧Agent E2E"边界内，是顺带修复的下游 bug。

**洞察**：E2E harness 的价值不在"评分"，在**暴露单环节 harness 测不到的端到端断链**。"脚本合格 = 下游可消费"，字段完整（DB 保真）+ 事实准确 + 语言达标才是硬门槛，时长只是参考。

### 真实生产验证（2026-08-13，命令行生成）

用 `cli/generate_drama.py` 真实生成「苏明成人物线」，产出 10 段 / 536 字，字段完整、事实 0 错、语言在线，落盘 + 入库成功。

超字数重写循环（`word_limit`）**标记为实验性功能**——实测会"矫枉过正"（697→131 字），但**这不影响生产级判定**：时长是参考指标，脚本短一点不影响下游消费。改进方向（可选）：双向重写 + 目标区间提示 + 最多 2 次迭代。
