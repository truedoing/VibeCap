## 1. 架构演化史

VibeCut 的架构不是一次性设计的，而是通过五个阶段逐步演化而来。每个阶段解决前一阶段的核心矛盾。

### 阶段全景

```
v0.1 — v0.5         v0.6 — v0.9          v0.10 — v0.12       v1.0 (当前)        v2.0 (目标)
│                    │                    │                    │                   │
│  脚本阶段           │  管线阶段           │  产品阶段           │  架构阶段          │  Agent 阶段
│                    │                    │                    │                   │
│  ┌──────────┐     │  ┌──────────┐      │  ┌──────────┐      │  ┌──────────┐      │  ┌──────────┐
│  │ 单文件    │     │  │ 多模块    │      │  │ 前后端    │      │  │ 分层架构  │      │  │ Agent    │
│  │ 脚本      │ →   │  │ 流水线    │ →    │  │ 分离      │ →    │  │ 明确定义  │ →    │  │ 自主编排  │
│  │ 手动执行  │     │  │ 半自动    │      │  │ Web UI    │      │  │ 方案论证  │      │  │ 人类监督  │
│  └──────────┘     │  └──────────┘      │  └──────────┘      │  └──────────┘      │  └──────────┘
│                    │                    │                    │                   │
│  核心矛盾:         │  核心矛盾:          │  核心矛盾:          │  核心矛盾:         │
│  能跑就行          │  流程能串起来        │  人能操作           │  架构能承载        │
│  vs                │  vs                 │  vs                 │  vs                │
│  每加一个功能       │  每步都要人工触发     │  人类决策太多        │  框架选型          │
│  就要改全局         │  流程不可见          │  AI 只是辅助        │  技术债务          │
└────────────────────┴────────────────────┴────────────────────┴───────────────────┘
```

### 阶段一：脚本阶段 (v0.1 — v0.5)

**特征：** 每个功能是一个独立 Python 脚本，手动依次执行。

```
analyze_episodes.py → cross_calibrate.py → build_index.py → server.py
       ↑                                                         ↓
   手动执行                                                 手动 curl 测试
```

**核心问题：** "我有一堆 AI 模型，怎么把它们用到视频剪辑里？"

| 做了什么 | 为什么 |
|----------|--------|
| BGE 语义搜索 | 不能用关键词搜视频画面，必须用语义 |
| faster-whisper 本地 ASR | 电视剧没有字幕，必须先转文字 |
| MiMo VLM 画面分析 | 画面内容需要结构化描述才能被搜索 |
| DeepSeek 脚本生成 | 从搜索结果到剪辑脚本需要 LLM 理解 |

**架构收获：** 确认了"视频→文本→向量→检索→生成"这条链路可行。

**架构缺陷：** 每个脚本独立运行，数据格式不统一，错误无法传递。

### 阶段二：管线阶段 (v0.6 — v0.9)

**特征：** 脚本串联成流水线，数据开始在模块间流动。引入 SQLite 统一状态管理。

```
数据库
  │
  ├── analyze_episodes   →  ASR/VLM 结果 →  sources/
  ├── cross_calibrate    →  校准结果     →  sources_clean/
  ├── clean_data         →  清洗合并     →  vlm_merged.json
  ├── build_index        →  BGE 向量     →  semantic_embeddings.npy
  └── server             →  搜索+API     →  HTTP :8765
```

**核心问题：** "数据怎么在模块间流转？质量怎么保证？"

| 做了什么 | 为什么 |
|----------|--------|
| SQLite 统一数据层 | 多个脚本需要共享状态（剧集元数据、任务进度） |
| 数据清洗管线 | ASR 原始输出质量差，需要 LLM 清洗和分类 |
| 质量评分体系 | 每集 ASR/VLM 质量参差，需要量化评估 |
| 交叉校准 | ASR 和 VLM 各自有盲区，双向校准提高准确率 |
| 加工面板 | 流水线步骤多，人类需要看到进度 |

**架构收获：** 数据流标准化。每个模块的输入/输出格式清晰定义，模块间通过文件系统 + SQLite 通信。

**架构缺陷：** 模块间的依赖是隐式的（通过文件路径约定），编排逻辑分散在 shell 脚本和 Python 代码中。

### 阶段三：产品阶段 (v0.10 — v0.12)

**特征：** 从"能跑的后端脚本"变成"有 UI 的产品"。React 前端 + SSE 流式响应。

```
浏览器                              服务器
┌──────────────┐                   ┌──────────────────────┐
│ PlanningDesk │── SSE 流式 ──────→│ script_agents.py     │
│  编剧台       │                   │  run_pipeline()      │
│              │←── 进度事件 ──────│  (4 Agent 链式调用)   │
├──────────────┤                   ├──────────────────────┤
│ VibeEdit     │── API 调用 ──────→│ server.py            │
│  分镜台       │                   │  BGE 搜索 / Chat     │
│              │←── 搜索结果 ──────│  精切 / 导出          │
└──────────────┘                   └──────────────────────┘
```

**核心问题：** "AI 能力怎么变成人类可用的产品？"

| 做了什么 | 为什么 |
|----------|--------|
| 三栏布局编剧台 | 素材列表 + 脚本编辑 + AI 助手，三个关注点分离 |
| SSE 流式响应 | Agent 链执行 30-60 秒，不能等全部完成才显示 |
| 精切引擎 | 粗段太长，需要精确到秒级的 sub_clips |
| 自动建轨 | 精切结果直接铺到时间轴，减少手动拖拽 |
| Elah 视频引擎 | 浏览器端预览 + 编辑，不需要桌面软件 |
| ChatPanel 多轮对话 | 搜素材不是一次性的，需要"换一个""不要这个" |
| 代理视频 | 1080p 原片太大，540p 代理让浏览器流畅播放 |

**架构收获：** 产品形态成立。AI 剪辑的四个核心节点（策划→精切→编辑→导出）都可以通过 UI 操作。

**架构缺陷：** 人类是编排者。每个节点之间需要人类点击按钮、审核结果、决定下一步。人类做了太多决策，AI 做了太少。

### 阶段四：架构阶段 (v1.0 — 当前)

**特征：** 停下来，重新审视架构。产品改名、技术方案论证、Agent 化设计。

**不再加功能，而是回答三个问题：**

1. VibeCut 的架构应该长什么样？
2. 当前的技术选型能支撑到多远？
3. 从"AI 辅助工具"到"AI 剪辑师"，缺什么？

| 做了什么 | 为什么 |
|----------|--------|
| 产品正式命名 VibeCut | 从项目代号到产品身份 |
| 全栈技术文档体系 | 架构知识从人脑转移到文档 |
| LangGraph + Agent 方案论证 | 现有 Agent 链需要升级为真正自主 Agent |
| RAG 知识体系建立 | 理解自研 BGE 方案在 RAG 生态中的位置 |
| Agent-first 架构设计 | 下一阶段的完整蓝图 |

**架构收获：** 确认了"Agent 编排 + 人类监督"是正确方向。现有代码 80% 可以复用（封装为 Tool）。

**当前状态：** 架构方案已完成论证，等待实施。

### 阶段五：Agent 阶段 (v2.0 — 规划中)

**特征：** 全应用由一个 Orchestrator Agent 编排，人类从操作者变为监督者。

```
人类: "剪一个60秒视频讲新东方教育理念"
  │
  ▼
┌─────────────────────────────────────────────┐
│           Orchestrator Agent                │
│                                             │
│  understand → plan → search → compose       │
│     │                              │        │
│     └── review ←── fix ←──────────┘        │
│                │                             │
│           [人类确认]                         │
│                │                             │
│          refine → build_timeline → export   │
└─────────────────────────────────────────────┘
```

**预期解决的问题：**
- 人类决策从 ~10 次降到 ~2 次（定义目标 + 最终确认）
- Agent 自我审核 + 自动修复，减少返工
- 跨任务学习：Agent 从历史任务中学习偏好

## 2. 关键技术决策 (ADR)

> ADR = Architecture Decision Record，记录每个关键决策的背景、选项、选择、后果。

### ADR-1: 为什么自研 BGE 索引，不用向量数据库？

**背景：** 需要对视频素材做语义检索。有两个选项：向量数据库（Chroma/Qdrant/Milvus）或纯 NumPy 内存方案。

**选项：**

| | NumPy 自研 | Chroma 嵌入模式 | Qdrant 独立服务 |
|---|---|---|---|
| 部署复杂度 | 零依赖 | pip install | Docker + 运维 |
| 查询性能 (<1万条) | <5ms | <10ms | <5ms |
| 元数据过滤 | 手动 | WHERE 语法 | 完整过滤 |
| 增量更新 | 重建全量 | 单条 insert | 单条 insert |
| 学习价值 | 理解向量检索底层 | 理解向量数据库抽象 | 理解分布式检索 |

**选择：NumPy 自研。**

**理由：**
1. 数据量 < 1 万条，NumPy 矩阵乘法 < 5ms，性能完全够
2. 零额外依赖，部署简单（对个人项目至关重要）
3. 从学习角度，`np.dot + np.argsort` 比调用 `collection.query()` 能理解更多
4. 不排除以后切 Chroma — 两者接口差异小，迁移成本低

**后果：**
- ✅ 架构简单，调试方便，所有逻辑在自己手里
- ⚠️ 增量更新需要重建全量索引（当前接受，以后可能成为瓶颈）
- ⚠️ 元数据过滤靠手动 list comprehension，复杂查询不够优雅

---

### ADR-2: 为什么用 http.server 而不是 Flask/FastAPI？

**背景：** Python 后端需要 HTTP API + SSE 流式。主流选择是 FastAPI。

**选项：**

| | http.server | Flask | FastAPI |
|---|---|---|---|
| 学习曲线 | 标准库，不用学 | 简单 | 需学 async/await |
| 性能 | 线程池，够用 | WSGI | ASGI 高性能 |
| SSE 支持 | 手动实现 | 插件 | 原生支持 |
| 依赖 | 0 | 1 | 3+ |
| 适合场景 | 学习/原型 | 小型应用 | 生产 API |

**选择：http.server。**

**理由：**
1. 项目的学习目的之一：理解 HTTP 协议和 SSE 的底层实现
2. 个人项目，并发量 < 5 用户，不需要 ASGI 性能
3. 手动实现路由、SSE、CORS 是很好的学习过程
4. 不依赖框架意味着理解每一行代码在做什么

**后果：**
- ✅ 深入理解了 HTTP 协议、SSE 流式、CORS 机制
- ⚠️ 路由是 if/elif 链，30+ 端点后维护成本上升
- ⚠️ 没有 OpenAPI 文档，API 靠 CLI 测试和文档维护
- ⚠️ 如果未来需要 WebSocket 或 gRPC，标准库不支持

**是否重新评估：** 如果引入 LangGraph Agent（需要 astream_events + SSE），FastAPI 的 async/await 支持会更自然。考虑在 Agent 化阶段迁移到 FastAPI。

### ADR-3: 为什么 Agent 编排选 LangGraph 而不是 CrewAI？

**背景：** 需要从"手动链式调用四个 Agent"升级为"有状态的自主 Agent 编排"。

**选项：**

| | LangGraph | CrewAI | Agno |
|---|---|---|---|
| 编程模型 | 显式状态图 | 角色扮演 + 自动委派 | 极简 Agent |
| 流程可控性 | 高（每个 node/edge 显式定义） | 中（Manager Agent 自动委派） | 低（Agent 自主决策） |
| 人机协作 | interrupt + resume 原生 | 需手动实现 | 需手动实现 |
| 状态持久化 | Checkpointer 内置 | 无 | 无 |
| 流式事件 | astream_events 原生 | 有限 | 有限 |
| 学习曲线 | 中（需理解 StateGraph 概念） | 低 | 低 |
| 生态兼容 | langchain-core + MCP | CrewAI 自有生态 | Agno 自有生态 |

**选择：LangGraph。**

**理由：**
1. VibeCut 的剪辑流程是确定性的（策划→选材→编辑→审核），不是开放协作。LangGraph 的显式图比 CrewAI 的自动委派更适合
2. Human-in-the-Loop 是刚需 — 脚本审核、精切确认必须人类确认。LangGraph 的 `interrupt()` 是原生支持
3. Checkpointer 让 Agent 执行可以中断恢复 — 用户关闭浏览器，明天打开继续
4. 学习价值：StateGraph 的编程模型（有向图 + 条件路由 + 状态持久化）是理解 Agent 系统设计的最佳入口

**后果：**
- ✅ 流程可预测、可调试、可审计
- ⚠️ 缺乏 CrewAI 的"涌现行为"（Agent 自主发现新策略）
- ⚠️ 需要手动定义每个 Node 和 Edge，模板代码较多

### ADR-4: 为什么 LLM 调用选 langchain-openai 而不是 LiteLLM？

**背景：** 需要调用 DeepSeek 和 MiMo 两个 API。

**选项：**

| | langchain-openai | LiteLLM | 原生 urllib |
|---|---|---|---|
| DeepSeek 兼容 | ✅ OpenAI 兼容 API | ✅ model="deepseek/chat" | ✅ 手动 payload |
| MiMo 兼容 | ✅ 同是 OpenAI 兼容 | ✅ model="mimo/mimo-v2.5" | ✅ 手动 payload |
| 与 LangGraph 集成 | ✅ 原生类型兼容 | ⚠️ 需要 LiteLLM adapter | ❌ |
| 重试/fallback | 需 LangChain callback | ✅ 内置 | ❌ 手写 |
| 依赖数 | 1 (langchain-openai) | 1 (litellm) | 0 |

**选择：langchain-openai（暂时）。**

**理由：**
1. LangGraph 已经是 Agent 层的基础设施，与 langchain-core 类型系统无缝兼容
2. DeepSeek 和 MiMo 都是 OpenAI 兼容 API，可以用同一个 `ChatOpenAI(base_url=...)` 切换
3. 保持依赖最小化 — 如果引入 LiteLLM，又多一个依赖

**后果：**
- ✅ 与 LangGraph 类型系统零摩擦
- ⚠️ 没有 LiteLLM 的跨 provider 重试和 fallback
- ⚠️ 如果以后要接入非 OpenAI 兼容的模型（如 Gemini），需要换方案

---

### ADR-5: 为什么不做知识库/文档问答型 RAG？

**背景：** RAG 最流行的应用场景是"上传 PDF，聊天问答"。VibeCut 显然不是。

**选择：领域特化 RAG，不做文档问答。**

**理由：**
1. VibeCut 的 RAG 是"搜视频素材"而非"搜文档" — 这是多模态 RAG（视频→文本→向量→检索），和文档问答是不同的产品品类
2. Chunking 策略完全不同：VibeCut 按说话人边界/场景边界切分，不是 token 窗口
3. 检索的评分维度不同：VibeCut 需要语义相似度 + 时间多样性 + 叙事角色匹配，不是单一的相似度
4. RAG 框架（LangChain/LlamaIndex）的文档加载器、chunking 策略、retrieval 模式对 VibeCut 的领域特性增值有限

**后果：**
- ✅ 检索系统完全定制化，匹配视频编辑的需求
- ⚠️ 无法复用 RAG 生态的工具（RAGAS 评估、LangFuse 追踪需要适配）
- ⚠️ Agentic RAG 的 SearchAgent 需要从零设计，不能直接套用 LangChain 的 `create_retrieval_chain`

## 3. 设计哲学

### 3.1 积木，不是黑盒

```
好的架构: 积木可拆卸                    坏的架构: 黑盒不可拆分

┌──┐ ┌──┐ ┌──┐                         ┌─────────────────┐
│搜│ │精│ │导│                          │                 │
│索│ │切│ │出│                          │    全功能       │
└──┘ └──┘ └──┘                          │    单体         │
  │     │     │                          │                 │
  └─────┼─────┘                          │  改一行坏全部    │
        │                                │                 │
   Agent 层 (新增)                        └─────────────────┘
```

**VibeCut 实践：**
- 每个模块独立可运行（`build_index.py`、`refine_segments.py`、`export_capcut.py` 都可单独执行）
- Agent 层是"胶水"，不侵入模块内部
- 可以关掉 Agent，回到手动模式，每一块积木仍然可用

### 3.2 架构复杂度与问题复杂度成正比

```
"任何系统的架构复杂度，应该刚好匹配它要解决的问题的复杂度，
 不多也不少。" 

问题复杂度            架构复杂度          状态
────────────────────────────────────────────────
"帮我搜一个镜头"      单文件脚本           ✅ 匹配
"搜镜头+写脚本+导出"  多模块流水线          ✅ 匹配
"我做视频剪辑产品"    前后端分离+UI         ✅ 匹配
"AI 替我剪视频"       Agent 编排           需要升级
```

**VibeCut 实践：** 不在不需要的时候引入框架。v0.1-0.13 一直没有用 LangChain，因为问题复杂度没有超过自研能解决的范围。现在到了 Agent 化阶段，LangGraph 引入是"问题复杂度驱动"的，不是"追框架"。

### 3.3 学习优先于便利

VibeCut 的双重身份：实际剪辑工具 + AI/ML 学习平台。

**这意味着：**

| 场景 | 普通项目会选 | VibeCut 会选 | 原因 |
|------|-------------|-------------|------|
| LLM 调用 | LiteLLM（最方便） | langchain-openai | 与 LangGraph 学习目标一致 |
| HTTP 服务 | FastAPI（最方便） | http.server（先用着） | 理解 HTTP/SSE 底层 |
| 向量检索 | Chroma（最方便） | NumPy（自研） | 理解向量检索原理 |
| Prompt 管理 | LangSmith（最专业） | .txt 文件 → LangChain PromptTemplate | 渐进学习 |

**这条原则的反面是：** 当学习目标达成后，应该切换到更成熟方案。NumPy BGE 索引理解了之后，该切 Chroma 就切；http.server 理解了之后，该切 FastAPI 就切。

### 3.4 人类不离开回路，但位置变了

```
当前:                                    目标:

人类 ──── 操作 ────→ 工具               人类 ──── 定目标 ────→ Agent
  │                      │                 │                      │
  ├── 点"生成"           │                 │                      ├── 理解意图
  ├── 审核脚本           │                 │                      ├── 设计方案
  ├── 点"精切"           │                 │                      ├── 执行剪辑
  ├── 审核 sub_clips    │                 审核 ←──────────────────┤
  ├── 点"导出"           │                 │      (只在关键节点)    │
  └── 手动调整           │                 └── 接收成片 ←─────────┘

人类做 80% 的决策                      人类做 20% 的决策
AI 做 20% 的执行                       Agent 做 80% 的执行+决策
```

**关键：** 人类始终在回路中。Agent 化不是"把人踢出去"，而是"把人从操作者升级为监督者"。

## 4. Agent-First Driven Development

### 4.1 什么是 AFDD

Agent-First Driven Development (AFDD) 是一套 AI 应用开发方法论。核心理念：

> **从 Agent 的能力边界出发设计系统，而不是从人类操作流程出发。**

它与传统开发模式的对比如下：

```
传统开发 (Human-First):                   AFDD (Agent-First):

1. 人类怎么做这个任务？                    1. Agent 能自主完成哪些子任务？
2. 把人类流程拆成步骤                      2. 哪些步骤必须人类决策？
3. 每个步骤写代码实现                      3. Agent 需要什么工具和信息？
4. 加上 AI 辅助（可选）                    4. 人类在哪些节点介入？
5. 测试人类操作体验                        5. 设计 Agent 决策 → 人类审批的循环
```

### 4.2 AFDD 的核心实践

#### 实践 1: 从 Agent Persona 出发

在写任何代码之前，先定义 Agent 的角色：

```
VibeCut Agent Persona:

"你是一位专业的视频剪辑导演。你的工作是——
- 理解剪辑需求
- 在素材库中搜索合适的镜头
- 设计叙事结构
- 编写剪辑脚本
- 输出可以直接导入剪映的草稿文件

你可以自主完成 80% 的工作。但在以下节点，你必须停下来等待导演确认:
- 脚本设计方案
- 精切的 KEEP/CUT 标注
- 最终成片导出"
```

这个 Persona 直接驱动：
- 哪些需要做成 Tool（Agent 需要操作的能力）
- 哪些需要做成 Human-in-the-Loop 节点（Agent 需要人类确认的节点）
- Agent 需要什么信息（素材元数据、用户偏好、历史案例）

#### 实践 2: 能力边界图

画一张图，标注 Agent 的自主区和人类决策区：

```
┌─────────────────────────────────────────────────────────┐
│                    Agent 自主区 (绿色)                    │
│                                                         │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ 搜索素材  │  │ 设计结构  │  │ 选择剪辑  │              │
│  │ (自主)   │  │ (自主)   │  │ (自主)   │              │
│  └──────────┘  └──────────┘  └──────────┘              │
│        │              │              │                   │
│        └──────────────┼──────────────┘                   │
│                       │                                  │
│                       ▼                                  │
│              ┌──────────────┐                            │
│              │  自我审核     │  ← Agent 内部循环           │
│              │  (评分+修复)  │    不经过人类               │
│              └──────┬───────┘                            │
│                     │                                    │
├─────────────────────┼────────────────────────────────────┤
│                     │    人类决策区 (红色)                  │
│                     ▼                                    │
│              ┌──────────────┐                            │
│              │  人类审核     │  ← 必须人类确认              │
│              │  [通过/修改]  │                            │
│              └──────────────┘                            │
│                     │                                    │
├─────────────────────┼────────────────────────────────────┤
│                     │     Agent 自主区 (绿色)              │
│                     ▼                                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ 精切引擎  │  │ 建时间轴  │  │ 导出草稿  │              │
│  │ (自主)   │  │ (自主)   │  │ (自主)   │              │
│  └──────────┘  └──────────┘  └──────────┘              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**这张图的规则：**
- 绿色区域：Agent 自主执行，人类不干预
- 红色节点：必须人类确认后才能继续
- Agent 内部的循环（审核→修复→再审核）在绿色区域内完成，不消耗人类的注意力

#### 实践 3: 工具优先于实现

在写 Agent 的 Node 逻辑之前，先把 Tool 定义清楚：

```
"Agent 需要什么能力？"  →  定义 Tool 的输入/输出 Schema
"Agent 需要什么信息？"  →  定义 State 的结构
"Agent 需要什么规则？"  →  定义 ConditionalEdge 的条件
```

只有当 Tool、State、Edge 都定义清楚后，才开始写 Node 的实现。这相当于在写"Agent 的 API 契约"。

#### 实践 4: 渐进自主

不是一次性把 Agent 做完美。而是按"自主程度"分阶段：

```
Level 1: 建议模式 (Suggestion)
  Agent: "我建议这样做，你看看行不行？"
  人类: 每次都确认

Level 2: 执行模式 (Execution)
  Agent: "我做了 A、B、C，这是结果"
  人类: 事后审核

Level 3: 自主模式 (Autonomy)
  Agent: "我完成了，导出在这里"
  人类: 只在异常时介入
```

每个 Level 的升级条件是：上一级的人类确认率 > 90%。

#### 实践 5: Agent 日志即文档

Agent 的每一步决策都要留下可读的日志：

```
不是:
  [DEBUG] search_materials: query='苏大强 老宅', results=5

而是:
  🎬 Agent: "我搜了'苏大强 老宅'，找到5个候选镜头。
    其中 EP1-3 有3个室内场景，EP38 有2个院子场景。
    我选了 EP38 的2个院子场景用于开场 Hook，
    因为用户要求'不要室内的'。"
```

**这有三个作用：**
1. 人类可以理解 Agent 为什么这样做
2. 出错时能快速定位是哪个决策出了问题
3. 长期来看，这些日志是"Agent 剪辑经验"的知识库

## 5. 架构原则

从演化史和决策记录中提炼的 6 条原则：

### 原则 1: 每个模块必须能独立运行

> 一个模块不应该依赖其他模块的运行时状态。它从文件/数据库读取输入，写入文件/数据库作为输出。

**原因：** 这样 Agent 可以按任意顺序组合模块，也可以跳过某些模块（如：不精切直接导出）。

### 原则 2: Agent 层是胶水，不是替代品

> Agent 编排层不修改现有模块的内部逻辑，只管理调用顺序和参数。

**原因：** Agent 可能出错。出错时，人类需要能绕过 Agent，直接使用底层模块。

### 原则 3: 状态显式化

> Agent 的所有决策依据都记录在 State 中。不存在"Agent 记得但人类不知道"的信息。

**原因：** 可审计、可调试、可恢复。LangGraph Checkpointer 就是干这个的。

### 原则 4: 默认自主，关键节点人类确认

> Agent 默认可以自主执行，但在三个节点必须等待人类：脚本设计、精切确认、最终导出。

**原因：** 平衡效率和安全性。这三个节点出错成本最高（脚本结构、素材选择、最终成片）。

### 原则 5: 数据流统一

> 所有模块的输入/输出格式通过文件系统 + SQLite 统一管理。不做进程间通信，不依赖内存状态。

**原因：** 简单、可靠。Agent 崩溃不影响已完成的工作。

### 原则 6: 渐进复杂度

> 当前复杂度刚好够解决当前问题。不为未来需求提前设计。

**原因：** v0.1-v0.13 的经验证明 — 提前设计的部分往往用不上，真正需要的部分之前没想到。
